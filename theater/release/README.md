# 版本候选回执

它解决一个具体问题：多个 AI 或人先后改动不同模块时，最后负责发行的人不能只凭聊天记录
猜“哪些已经完成、哪些应该进入公开版”。

## 怎么留下痕迹

完成一项代码工作后，在 `candidate.json` 增加一张回执，至少写明：

- `id`：稳定、短、不可重复的编号；
- `title`：普通人能看懂的改动名称；
- `status`：`ready`（待验证）、`verified`（已验证）、`deferred`（明确延期）或
  `private`（只留在私有数据层）；
- `files`：实际涉及的仓库相对路径；
- `tests`：做过或发布前必须做的验证；
- `public_release`：是否应该进入公开发行版；
- `notes`：特殊同步方式、隐私边界或尚未解决的问题。

`private_base_commit` 记录本轮开始时私有仓的提交。检查器会同时查看从它到当前 HEAD 的
提交、暂存区、尚未暂存的修改和新文件，因此另一位 AI 的工作无论停在哪一步，都不会从候选清单里消失。

不要把模型聊天摘要当回执，也不要在回执里写本机绝对路径、作品正文、回执原文或私人数据。

## 发布前检查

在私有开发仓运行：

```text
python theater/release/check_candidate.py --public-root <公开仓目录> --require-verified
```

检查器会对照两个文件树的发行允许清单。只要存在一份未登记的差异、目标版本不一致、
回执仍是 `ready`，发布就会失败。公开发行完成后，把本次 `candidate.json` 复制为
`archive/v<版本>.json`，再为下个版本建立新候选表；已归档回执不改写。

私有开发日志和公开脱敏文档本来就可能不同：这类改动必须另列一张
`status: "private"`、`public_release: false` 的回执。检查器会把它视为“已经明确处置”，
但不会要求复制到公开仓；既不会漏项，也不会为了清零差异误传私人批次或作者数据。
